## 2. Тестлэгдэх функц ба түүний шийдвэрийн дараалал

Гол тестлэгдэх функц: **`POST /registrations`** (хичээлд бүртгүүлэх).

`server.js`-ийг уншиж, мөн curl-ээр туршиж үзэхэд уг функц нөхцөлүүдийг **тогтсон дарааллаар** шалгаж, таарсан эхний алдааг буцаадаг нь тогтоогдсон:

```
1. studentID эсвэл courseID талбар дутуу     → 400 ERROR_BAD_REQUEST
2. оюутан олдохгүй                            → 200 ERROR_NO_STUDENT
3. оюутны status ≠ "active"                   → 200 ERROR_INACTIVE_STUDENT
4. хичээл олдохгүй                            → 200 ERROR_NO_COURSE
5. урьдач нөхцөл дутуу                        → 200 ERROR_PREREQUISITES + missing[]
6. бусад тохиолдолд                           → 201 OK + registrationID
```

Энэ дараалал нь зааварт бичигдээгүй тул **туршилтаар** тогтоосон (Даалгавар 2-ын "давхар алдааны хослол"): идэвхгүй оюутан + байхгүй хичээл гэсэн хоёр алдааг зэрэг үүсгэхэд `ERROR_INACTIVE_STUDENT` буцсан, өөрөөр хэлбэл оюутны шалгалт эхэлж явагддаг тул хичээлийн алдаа "нуугдсан".

## 3. Даалгавар 2 — Тест дизайн

### 3.1 Сонголтууд ба эквивалент ангиуд

| Сонголт | Эквивалент ангиуд | Тайлбар |
|---|---|---|
| `studentID`-гийн хүчинтэй байдал | (1) бүртгэлтэй оюутан, (2) бүртгэлгүй ID, (3) талбар огт дутуу | (3) нь форматын алдаа тул 400 руу салбарлана |
| Оюутны төлөв (`status`) | (1) `"active"`, (2) өөр ямар ч утга (`"inactive"`, `"suspended"` г.м.) | Код `status !== "active"` гэж шалгадаг тул бүх "бусад" утга нэг анги |
| `courseID`-гийн хүчинтэй байдал | (1) бүртгэлтэй хичээл, (2) бүртгэлгүй ID, (3) талбар огт дутуу | |
| Урьдач нөхцөл vs оюутны `coursesTaken` | (1) хичээл урьдач нөхцөлгүй (`[]`), (2) бүх урьдач нөхцөлийг үзсэн, (3) зарим нь дутуу, (4) огт үзээгүй | (1) ба (2) хоёулаа 201 өгдөг ч өөр замаар — (1) нь хязгаарын тохиолдол |

10 дугаар спецификаци (буруу JSON) нь анх миний дизайнд ОРООГҮЙ байсан бөгөөд 7-р хэсгийн AI харьцуулалтын явцад илэрч нэмэгдсэн — дэлгэрэнгүйг тэндээс үз.

## 4. Даалгавар 1 ба 3 — Collection

[`lab05-collection.json`](lab05-collection.json) — Postman collection v2.1.

* Спецификаци бүр = тусдаа **хавтас** (нийт 10 + нийтийн API-гийн 1 = 11 хавтас), доторх дараалал: `PUT /students/:id` → `PUT /courses/:id` → `POST /registrations`.
* **Тест бүр бие даасан**: өөрийн setup-аа өөрөө хийдэг тул дарааллаас хамаарахгүй. `PUT` нь бичлэгийг бүхэлд нь дахин бичдэг (idempotent) учир дахин ажиллуулахад аюулгүй.
* Setup хүсэлт бүрд "200 OK" гэсэн нэг oracle тавьсан — ингэснээр тест унавал setup буруудсан эсэхийг шууд ялгана.
* `POST` бүрд **хоёроос гурван oracle**: (1) статус код, (2) `result` утга, (3) шаардлагатай үед `missing` массив эсвэл `registrationID`-гийн төрөл.
* `registrationID`-ийн ЯГ утгыг шалгаагүй — зөвхөн `to.be.a("number")`. Сервер in-memory тул дугаар ажиллуулалт бүрт хуримтлагддаг ба `== 1` гэж шалгавал хоёр дахь удаад л унах байсан.
* URL бүр `{{baseUrl}}` collection хувьсагчийг ашиглана.

## 7. Нэмэлт даалгавар — AI өнцөг

`server.js`-ээ өөр AI туслахад өгөөд Лекц 5-ын процессын дагуу "сонголтуудыг тодорхойлж, эквивалент ангид хуваагаад, ангиудын хослолоор Postman тестүүд үүсгэ" гэж хүссэн (хязгаар, алдааны дараалал талаар сануулга өгөөгүй). Гарсан үр дүнг өөрийн дизайнтай тулгасан дүгнэлт:

**(1) AI ямар сонголт, ангийг мартсан бэ?** Үндсэн сонголтуудыг (оюутны хүчинтэй байдал, төлөв, хичээлийн оршин байдал, урьдач нөхцөл) бүгдийг олсон ба энэ API-гийн СОНИРХОЛТОЙ статусын семантикийг (201 = амжилт, 200 = бизнес логикийн алдаа, 400 = форматын алдаа) зөв таньсан — REST-ийн ердийн хэвшлээр "оюутан олдсонгүй → 404" гэж андуураагүй нь сайшаалтай. Гэхдээ **давхар алдааны хослолыг тестийн тохиолдол болгоогүй**: шалгалтын дараалал байдгийг зөвхөн төгсгөлийн "нэмэлт" жагсаалтад нэг өгүүлбэрээр дурдсан бөгөөд TC01–TC10 матрицад нь ийм тест алга. Миний дизайнд энэ нь 7 дугаар хавтас болж, хамгийн чухал нээлт болсон.

**(2) Миний мартсаныг AI олсон уу? — ТИЙМ.** AI-гийн TC10 нь **буруу бүтэцтэй JSON** (`ERROR_BAD_JSON`) илгээх тохиолдлыг санал болгосон бөгөөд энэ нь миний анхны 9 спецификацид огт байгаагүй. Зааврын хариуны хүснэгтэд уг тохиолдол бичигдсэн атлаа би `ERROR_BAD_REQUEST` (талбар дутуу) гэдэгтэй нь андуураад орхисон байсан. Үүнийг хүлээн зөвшөөрч **10 дугаар хавтас** болгон collection-д нэмсэн ба үүний үр дүнд спецификацийн тоо 9-өөс 10 болж, нийт assertion **39** болсон (`results/newman-pass.txt`). Энэ бол AI-гийн гаргасан ганцхан жинхэнэ шинэ олдвор байв.

**(3) AI-ийн oracle-ууд зөв байсан уу?** Статус кодын хүлээлтүүд нь зөв, харин oracle-ийн ЧАНАР сул байсан: (а) `pm.expect(body.registrationID).to.exist` нь мөр, `true` зэрэг ямар ч утгад биелэх тул миний `to.be.a("number")`-оос сул; (б) `missing` массивыг `.to.include("C002")` гэж шалгасан нь сервер `["C001","C002"]` гэж БУРУУ хариу өгсөн ч PASS болно — миний `to.eql(["CS202"])` энэ алдааг барина; (в) `{{baseUrl}}` хувьсагч ашиглаагүй, URL-уудыг шууд бичсэн нь зааврын шаардлагад нийцэхгүй.

**Хамгийн том зөрүү — тестийн бие даасан байдал.** AI нь бүх setup-аа эхэнд нэг удаа ажиллуулдаг "Initialization" блок болгон санал болгосон; миний хувилбарт setup нь хавтас бүрийн дотор байдаг. AI-гийн бүтцэд TC05-ыг дангаар нь ажиллуулбал өгөгдөл байхгүй учир тест унах байсан — энэ нь Лекц 4-ийн test independence зарчмыг зөрчиж байна. Товчдоо: AI миний санаагүй нэг тохиолдлыг олж өгсөн нь үнэ цэнэтэй, гэхдээ түүний oracle-ийн нарийвчлал ба тестийн бүтэц нь миний хувилбараас сул байв.

## 8. Дүгнэлт

Дизайны таван алхмаас хамгийн их бодол шаардсан нь **сонголтуудыг эквивалент ангид хуваах** алхам байлаа, учир нь `status` талбарын хувьд `"inactive"`, `"suspended"`, `"xyz"` гэх бүх утга кодын хувьд НЭГ анги болохыг ойлгох хэрэгтэй байсан бөгөөд үүнийг зөвхөн шаардлагыг уншаад биш, серверийн шалгалтыг ойлгож байж шийдсэн. Хоёр дахь хүнд алхам нь ангиудын хослолоос аль нь утга учиртайг сонгох явдал байв: онолын хувьд 3×2×3×4 = 72 хослол гарах ч ихэнх нь нэг ижил алдааны замаар дуусдаг тул 10 спецификаци хангалттай байсан. Хамгийн сонирхолтой нээлт бол **боломжгүй биш, харин "нуугддаг" хослол** байсан — идэвхгүй оюутан + байхгүй хичээл гэсэн хоёр алдааг зэрэг үүсгэхэд зөвхөн `ERROR_INACTIVE_STUDENT` буцаж, хичээлийн алдаа огт илэрдэггүй. Энэ нь API нэг хүсэлтэд зөвхөн нэг алдаа буцаадаг гэсэн далд шаардлагыг илрүүлсэн бөгөөд зааварт тэр нь бичигдээгүй байсан тул тестээрээ тогтоосон. Миний тестүүд серверээс согог олоогүй: 39 assertion бүгд PASS болсон нь хэрэгжүүлэлт спецификацитайгаа нийцэж байгааг харуулсан. Гэхдээ "бүх тест ногоон" гэдэг нь тестийн чанарын баталгаа биш тул зориуд буруу oracle-тай collection-оор шалгахад exit code 1 гарч, quality gate ажиллаж байгаа нь батлагдсан. DOWN ажиллуулалт нь хамгийн сургамжтай нь байлаа: 36 assertion унасан ч энэ нь системийн логикийн алдаа биш, холболтын алдаа байсан бөгөөд хоёрыг ялгаж ойлгохгүй бол CI дээр "тест унав" гэсэн мэдээллийг буруу тайлбарлах эрсдэлтэй. Мөн `registrationID`-ийн яг утгыг шалгахгүй байх шийдвэр нь тестийг дахин ажиллуулахад тогтвортой болгосон — in-memory сан дээр дугаар хуримтлагддаг тул `== 1` гэсэн oracle хоёр дахь удаад л унах байсан. Эцэст нь Даалгавар 5-ын нийтийн API нь setup шаардахгүй тул хялбар ч, өгөгдөл нь миний хяналтаас гадуур учир oracle нь эмзэг байдгийг харуулсан. Мөн 7-р хэсгийн AI харьцуулалт нь миний дизайнаас буруу JSON-ы тохиолдол дутсаныг илрүүлсэн тул түүнийг 10 дугаар хавтас болгон нэмсэн (нийт 39 assertion).

## 10. AI ашиглалтын тэмдэглэл

Энэ лабораторид AI туслахыг тестийн дизайныг хэлэлцэх, collection-ий JSON-ыг бүтээхэд ашигласан. Серверийн шийдвэрийн дарааллыг curl-ээр өөрөө туршиж тогтоосон бөгөөд Newman-ы гурван ажиллуулалтыг өөрийн машин дээр гүйцэтгэж, үр дүнгийн файлуудыг шалгасан.
